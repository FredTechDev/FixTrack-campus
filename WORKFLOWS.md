# FixTrack Campus — End-to-End Workflows

Every workflow follows the same rule: **pages read, actions write**. Each write runs in a PDO transaction, records a status history entry where relevant, creates notifications, then redirects (Post/Redirect/Get).

Code paths use `__DIR__`, so `actions/x.php` reaches helpers via `../includes/bootstrap.php`, while root pages use `includes/...`.

---

## 1. Registration → login → logout

| Step | Detail |
|---|---|
| 1 | Guest opens `register.php`. CSRF token generated by `csrf_token()` in `includes/auth.php`. |
| 2 | Form validates in browser (`assets/js/validate.js`), then server-side in `register.php`. |
| 3 | Email uniqueness checked with a prepared `SELECT`; password checked against `^(?=.*[a-z])(?=.*[A-Z])(?=.*\d).{8,}$`. |
| 4 | `password_hash($password, PASSWORD_DEFAULT)` → INSERT into `users` with `role='student'`. |
| 5 | Flash "Account created" → redirect to `login.php`. |
| 6 | `login.php`: `validate_csrf()`, `password_verify()`, `is_active` check, session brute-force counter (8 attempts / 5 min). |
| 7 | `login_user()` calls `session_regenerate_id(true)` and stores identity in `$_SESSION`. |
| 8 | `dashboard.php` routes by role: admin → `admin/dashboard.php`, technician → `technician/dashboard.php`, student → `student/dashboard.php`. |
| 9 | `logout.php` → `logout_user()` clears `$_SESSION`, expires the cookie with `setcookie(..., time()-42000, ...)`, `session_destroy()`. |

**Evidence:** verified live — after login the dashboard returned `200`; after `logout.php` the dashboard returned `302 http://localhost:8085/login.php`; the cookie jar contained zero session cookies. Test cases A1–A11 in `TESTING.md`.

## 2. Student submits a report

| Step | Detail |
|---|---|
| 1 | `student/report-new.php` renders selects from `get_categories()` / `get_facilities()`. `facility` and `category` GET params (from QR links) pre-select values. |
| 2 | While typing the title, `app.js` debounces 500 ms and calls `api/duplicate-check.php?q=…`, which returns up to 3 similar reports as JSON. Advisory only. |
| 3 | POST → `actions/report-create.php` → `require_role(ROLE_STUDENT)` → `require_post()` (POST + CSRF). |
| 4 | Server validation: active category/facility, title 5–200, description 10–5000, room ≤ 100, priority in `PRIORITIES`, max 5 files. |
| 5 | `handle_multiple_image_uploads()` → `handle_image_upload()`: real MIME via `finfo`, allow-list jpg/png/webp, ≤ 5 MB, random `bin2hex(random_bytes(16))` filename into `uploads/evidence/`. |
| 6 | Transaction: `generate_tracking_code()` retries `FTC-{year}-{5 digits}` on collision; INSERT `reports` (status `REPORTED`); INSERT `report_images`; `record_status_change(null → REPORTED)`; notify all active admins. |
| 7 | Flash carries the tracking code → redirect to `student/report-view.php?id=N`. |

**Evidence:** automated submission returned `302 → student/report-view.php?id=9` with code `FTC-2026-29531` and status `REPORTED`; uploaded PNG stored as `uploads/evidence/<random>.png` and fetched with HTTP 200; XSS title rendered as `&lt;script&gt;` (0 raw script tags, 1 escaped). Test cases C1–C12.

## 2b. Guest reports (no account)

| Step | Detail |
|---|---|
| 1 | Open `guest-report.php` from the landing page, login page or a QR poster (`?facility=N` pre-selects the building). |
| 2 | Form asks for name, optional email, issue details, priority and photos. CSRF token still required. |
| 3 | POST → `actions/guest-report-create.php` → `require_post()` (no role check — this endpoint is public). |
| 4 | Same server validation and upload checks as student reports. |
| 5 | Generates `bin2hex(random_bytes(24))` (48 hex chars) as `guest_token`; INSERT report with `student_id = NULL`, `is_guest = 1`, guest name/email; history + admin notifications. |
| 6 | Redirect to `guest-receipt.php?code=…&token=…` showing the tracking code and a **private tracking link**. |
| 7 | `track.php` validates code **and** token through `get_guest_report()` — no session, no account. Shows details, stepper, history and photos. |
| 8 | When `RESOLVED`, `actions/guest-verify.php` records the rating/feedback in history and moves to `VERIFIED` or back to `IN PROGRESS`. When `VERIFIED`/`CLOSED`, `actions/guest-reopen.php` reopens with a reason. |
| 9 | Staff workflow is unchanged: `get_report()` uses `LEFT JOIN users` + `COALESCE(u.full_name, r.guest_name)`, admin lists show a "Guest" badge, and notifications to a non-existent student are skipped. |

**Evidence:** live run — guest POST returned `302` to the receipt with code `FTC-2026-73167` and a 48-char token; receipt and tracking pages returned 200 with no PHP warnings; a bad token did not reveal the report. Full cycle observed: `REPORTED → APPROVED → ASSIGNED → IN PROGRESS → RESOLVED → VERIFIED → CLOSED → IN PROGRESS`, with `student_id = NULL` and `is_guest = 1` in the final row. Export contains an `Is Guest` column with value `yes`.

**Claiming later:** registering with the same email runs one `UPDATE` in `register.php` that sets `student_id`, clears `is_guest` and the token, and moves any guest photos to the new owner. Verified: report moved from `student_id = NULL / is_guest = 1` to the new account with `guest_token = NULL`; the old private link then showed "Invalid or expired link", and the report appeared on the student dashboard.

## 3. Admin reviews (approve / under review / reject)

| Step | Detail |
|---|---|
| 1 | `admin/reports.php` lists all reports with status/category/facility/priority/technician/keyword filters and pagination. |
| 2 | `admin/report-view.php?id=N` shows details, workflow stepper, evidence gallery, history and the review form. |
| 3 | POST `decision` = `review` / `approve` / `reject` → `actions/report-review.php`. |
| 4 | `is_valid_status_transition(current, target)` must pass; rejection requires a 5+ char reason. |
| 5 | `approve` sets `status=APPROVED`, `deadline = NOW() + INTERVAL priority_hours HOUR` (12/24/48/96h), clears rejection reason. |
| 6 | `reject` stores `rejection_reason`, clears deadline, notifies the student with the reason. |
| 7 | Transaction writes status + `status_history` + notification. |

**Evidence:** live transition `REPORTED → APPROVED` returned `302`; deadline and history row written; rejection without a reason is blocked (test W4). Test cases W1–W4.

## 4. Admin assigns / reassigns a technician

| Step | Detail |
|---|---|
| 1 | Only `APPROVED` or `ASSIGNED` reports can be assigned. |
| 2 | `get_technicians($pdo, $category_id)` sorts specialists for the category first. |
| 3 | POST → `actions/report-assign.php`: validates active technician and 1–720 h deadline. |
| 4 | Transaction: existing non-completed assignments marked `reassigned`; new `assignments` row inserted; report → `ASSIGNED` with new deadline; history note names the technician; technician **and** student notified. |
| 5 | `get_report_assignment()` filters `status <> 'reassigned'`, so detail views always show only the current technician. |

**Evidence:** live `APPROVED → ASSIGNED` returned `302`; assignment row created with `deadline_hours=24`; both users received notifications. Test cases W5–W6.

## 5. Technician starts and resolves a job

| Step | Detail |
|---|---|
| 1 | `technician/dashboard.php` and `jobs.php` list only assignments where `technician_id = session uid` and `status <> 'reassigned'`, ordered by priority then deadline. |
| 2 | `technician/job-view.php?id=N` re-checks ownership before rendering. |
| 3 | **Start**: POST `action=start` → `actions/technician-update.php`; assignment → `in_progress`, report → `IN PROGRESS`, history + student notification. |
| 4 | **Resolve**: requires 10+ char repair notes. Completion photos uploaded to `uploads/completion/` as `image_type='completion'`. Assignment → `completed` + `completed_at`; report → `RESOLVED` + `resolved_at`; student gets `verification_needed`, admins get "job resolved". |

**Evidence:** live `ASSIGNED → IN PROGRESS → RESOLVED` returned `302` each; completion rows linked to the report and uploader. Test cases W7–W9.

## 6. Student verifies, closes, or reopens

| Step | Detail |
|---|---|
| 1 | Only the reporter, only when status is `RESOLVED`, rating 1–5. |
| 2 | **Satisfied**: `actions/report-verify.php` upserts `repair_verifications` (`ON DUPLICATE KEY UPDATE` supports re-verification after reopen), report → `VERIFIED` + `verified_at`, admins notified to close. |
| 3 | **Unsatisfied**: requires 10+ char feedback, stores `is_satisfied=0`, report returns to `IN PROGRESS`, `resolved_at` cleared, assignment reactivated, technician + admins notified. |
| 4 | **Close**: admin posts to `actions/report-close.php`; only `VERIFIED → CLOSED`, sets `closed_at`, notifies student. |
| 5 | **Reopen**: from `VERIFIED` or `CLOSED`, `actions/report-reopen.php` requires a 10+ char reason, returns to `IN PROGRESS`, clears resolution timestamps and notifies technician + admins. |

**Evidence:** live sequence `RESOLVED → VERIFIED → CLOSED → IN PROGRESS` returned `302` at every step and produced 11 notification rows for one report. Test cases W10–W15.

## 7. Status history & notifications (cross-cutting)

- `record_status_change()` inserts `old_status`, `new_status`, `notes`, `changed_by`, `created_at` into `status_history`.
- `create_notification()` inserts per-user alerts with `report_id`, `type` and `is_read=0`.
- `includes/header.php` shows the unread count badge; `notifications.php` lists alerts and posts to `actions/notification-read.php` to mark one or all read.
- All three detail views render the history as a timeline; `workflow_stepper()` paints the eight-step progress bar from `WORKFLOW_STEPS`.

**Evidence:** observed audit trail for a full lifecycle:

```
NULL       -> REPORTED
REPORTED   -> APPROVED
APPROVED   -> ASSIGNED
ASSIGNED   -> IN PROGRESS
IN PROGRESS-> RESOLVED
RESOLVED   -> VERIFIED
VERIFIED   -> CLOSED
CLOSED     -> IN PROGRESS
```

Notifications generated in that run included `New report`, `Report update`, `New job assigned`, `Work in progress`, `Repair completed - verification needed`, `Repair verified`, `Report closed`, `Issue reopened`.

## 8. Search, filter, export

- All list pages whitelist GET filters, build `WHERE` clauses with prepared bindings, and paginate with `COUNT(*)` + `LIMIT/OFFSET`.
- `export.php` is role-scoped (students see only their own rows), applies the same filters, streams CSV via `php://output` with a UTF-8 BOM, and prefixes `= + - @` values with `'` against formula injection.
- Admin reports uses a correlated subquery for technician name to satisfy MySQL 8 `only_full_group_by`.

**Evidence:** SQLi string `' OR 1=1--` returned HTTP 200 and was treated as a literal; CSV exports for admin and student both returned headers including `Tracking Code`. Test cases D5–D11.

## 9. Admin CRUD + QR + analytics

- `actions/user-save.php`, `facility-save.php`, `category-save.php`: create/update with validation, unique-email/code/slug checks, bcrypt for new/given passwords, cannot deactivate self.
- `admin/qr-codes.php` renders elements with `data-qr-url`; `assets/js/qr.js` draws QR codes with vendored qrcodejs. `qr/facility.php` prints a label; the encoded URL pre-fills `student/report-new.php?facility=N`.
- `admin/analytics.php` computes status counts, category bars, average resolution time and satisfaction from live aggregates.

**Evidence:** minimal seed = 3 users / 2 facilities / 8 categories / 3 reports / 2 assignments / 8 history rows / 3 notifications; analytics page loads without PHP errors. Test cases M1–M7, D4.

## 10. Security workflow (every request)

1. `require_role()` on page **and** action.
2. Ownership check on reads and writes (`student_id`, `technician_id`).
3. `require_post()` = POST only + `hash_equals` CSRF check.
4. All user input re-validated server-side; all SQL prepared; all output through `e()`.
5. Uploads checked by `finfo`, size, random names, and `uploads/.htaccess` blocks script execution.

**Evidence:** student → admin page = 403; technician → admin page = 403; student → admin action = 403; missing/forged CSRF = 403; guest → dashboard = 302 login; cross-user report/job = 302 to own list; `GET /uploads/evil.php` = 403. Test cases R1–R8, C9, C12.
